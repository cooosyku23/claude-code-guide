# Claude Fable 5 のプロンプティング：解説・日本語訳・実践ガイド

Claude Fable 5 は、従来のモデルでは複雑すぎたり、長時間かかりすぎたり、曖昧すぎたりした問題に取り組めるモデルで、人間が数時間から数週間かけて完了するようなエンドツーエンドの作業で特に力を発揮します。Anthropic によれば、最良の成果を得ているチームは Claude Fable 5 を最も困難な未解決の問題に適用しており、単純なワークロードだけでテストすると能力範囲を過小評価しがちです（より単純なタスクでも確実に機能します）。その一方で、Claude Opus 4.8 とは異なる動作上の特徴がいくつかあり、プロンプトやスキャフォールディングの更新が必要になる場合があります。

能力が上がったぶん「1ターンが長くなる」「自律的に動く」といった変化が生まれ、それを御するための指示が各項目のテーマになっています。以下は、Anthropic公式ドキュメント「[Claude Fable 5 のプロンプティング](https://platform.claude.com/docs/ja/build-with-claude/prompt-engineering/prompting-claude-fable-5)」で示された、調整が最も頻繁に必要となる動作とサンプルプロンプトを、要点と日本語訳の形で順を追ってまとめたものです。
なお、原典は Claude Fable 5 と Claude Mythos 5 の両方を対象としていますが、本ガイドは Claude Fable 5 に絞って解説します（原典照合日：2026年6月10日）。
末尾には本ガイド独自の付録として、どのパターンから導入すべきかを整理した「付録A: 移行チェックリスト」、各パターンを Claude Code の具体的な機能へ落とし込む「付録B: Claude Code への適用レシピ」、そして既存スキルの棚卸し（パターン15）を実行可能なスラッシュコマンドにした「付録C: 同梱スキル `/fable5-tune`」を収録しています。

## このガイドの使い方

本ガイドのサンプルプロンプトの多くは、恒常的に効かせたい指示としてシステム層に置くことを想定しています。
Claude API で直接ハーネスを構築している場合はシステムプロンプトへ、Claude Code で使う場合は `CLAUDE.md`（適用対象を絞りたい場合はスキルやサブエージェント定義）へ追加してください。
ただし、9番（メモリのブートストラップ）と12番（理由を伝える）は依頼のたびにユーザーメッセージとして送るテンプレートであり、14番（ユーザー送信ツール）はハーネスに組み込むツール定義です。
10番（早期停止対策）のように自律パイプライン向けと明記されたものは、各ターンに注入されるシステムリマインダーとして追加します（Claude Code では hooks 機能によるコンテキスト注入で、自作ハーネスでは各ターンのユーザーメッセージへ定型文を付加することで実現できます。具体的な設定例は付録Bを参照してください）。
サンプルプロンプトの日本語訳はそのまま貼って使えますが、原典に記載された効果検証（例：5番の「捏造された進捗報告がほぼ完全に排除された」）は英語原文のプロンプトに対して行われたものです。
検証済みの文言を厳密に再現したい場合は、原典から英語原文をコピーしてください。

また、Claude Fable 5 は攻撃的サイバーセキュリティ技術、生物学・ライフサイエンス関連のコンテンツ、およびモデルの要約された思考の抽出を対象とする安全性分類器を実行しており、無害なサイバーセキュリティ作業や有益なライフサイエンスのタスクでもこれらが作動して `stop_reason: "refusal"` が返ることがあります。
API で利用する場合は、拒否されたリクエストを Claude Opus 4.8 へ自動的に再ルーティングするサーバーサイドまたはクライアントサイドのフォールバック設定が公式に推奨されています。

## 前提：Claude Opus 4.8 からの能力向上

原典は、個別のプロンプティングパターンの前提として、Claude Opus 4.8 と比較した次の向上点を挙げています。

- **長期的な自律性** — 数日にわたる目標指向の実行を、長く複雑なタスク全体で指示を強く保持したまま完了する。
- **複雑で明確に定義された問題に対する初回の正確性** — 以前は数日間の反復を要したシステムを、シングルパスで実装できたという初期テスターの報告がある。
- **ビジョン** — 密度の高い技術画像や詳細なスクリーンショットを大幅に高い精度で解釈し、反転・ぼやけ・ノイズのある画像には bash ツールやクロップツールを使うよう訓練されている。
- **エンタープライズワークフロー** — 財務分析、スプレッドシート、スライド、ドキュメントで、スコープ内に留まりプロフェッショナルレベルの出力を生成する。
- **コードレビューとデバッグ** — バグ発見の再現率が Claude Opus 4.8 より顕著に高く、コードベースやリポジトリ履歴全体の検索も含む。
- **曖昧さへの対処** — 複雑で複数のスレッドを持つリクエストから次のステップを判断する場面に強い。
- **委任と協調** — 並列サブエージェントのディスパッチと維持の信頼性が大幅に向上し、長時間実行されるサブエージェントやピアエージェントとの継続的なコミュニケーションを確実に管理する。

まず最初に直面するのが、実行時間そのものの長さです。

## 1. デフォルトでより長いターン

**解説（要点）：**

- 高エフォートでは1リクエストが数分、自律実行は数時間に及ぶことがある。
- 移行前にクライアントのタイムアウト・ストリーミング・進捗インジケーターを調整し、ブロッキングではなく非同期で実行状況を確認できるハーネスに再構築する。
- このプロンプトは、タスクが曖昧なときの過剰な計画立てを防ぐためのもの。

**日本語訳：**

```
行動するのに十分な情報がそろったら、行動してください。
会話の中ですでに確定した事実を再導出したり、ユーザーがすでに下した決定を蒸し返したり、追求しない選択肢をユーザー向けメッセージで並べ立てたりしないでください。
選択を検討しているなら、網羅的な比較ではなく推奨を示してください。
これは思考ブロックには適用されません。
```

ターンの長さや深さを根本から左右するのが、次のエフォート設定です。

---

## 2. すべてのエフォートレベルを検討する

**解説（要点）：**

- エフォートは知能・レイテンシ・コストのトレードオフを制御する主要手段。
- 既定は `high`、最重要ワークロードは `xhigh`、日常作業は `medium`／`low`。
- 低エフォートでも従来モデルの `xhigh` を上回ることが多い。
- 高エフォートの日常作業は、必要以上にコンテキストを収集・熟考しがち。
- 同時に、高エフォートは優れた検証動作、洗練された推論、最も厳密な出力を生むことも多い（やりすぎとのトレードオフ）。
- このプロンプトは、高エフォート時の要求外の整理・リファクタを抑制する。

**日本語訳：**

```
タスクが必要とする以上の機能追加・リファクタ・抽象化の導入はしないでください。
バグ修正に周辺のクリーンアップは不要であり、一度きりの処理に通常ヘルパーは要りません。
架空の将来要件に向けた設計はせず、うまく動く最も単純な方法を取ってください。
早すぎる抽象化や中途半端な実装は避けてください。
起こり得ないシナリオのためのエラー処理・フォールバック・バリデーションは追加しないでください。
内部コードとフレームワークの保証は信頼してください。
バリデーションはシステム境界（ユーザー入力、外部API）でのみ行ってください。
コードを変更すれば済む場合に、フィーチャーフラグや後方互換のためのつなぎ（shim）を使わないでください。
```

高エフォートで生じがちな「やりすぎ」は、改善した指示追従力を使えば短い指示で抑えられます。ここからは、その指示追従に関するパターンが続きます。

---

## 3. 強力な指示追従（簡潔さ）

**解説（要点）：**

- 指示追従が改善し、各挙動を列挙せずとも簡潔な指示でほぼ制御できる。
- 高エフォートでは必要以上に詳述しがち（不採用案の調査、長い根本原因の説明など）。
- 簡潔さに関する短い指示は、パターンを逐一列挙するのと同等に効く。

**日本語訳：**

```
結果から始めてください。
作業を終えた後の最初の一文は、「何が起きたか」または「何が分かったか」——ユーザーが「とにかく要点だけ教えて」と言ったときに求めるもの——に答えるべきです。
補足の詳細や理由付けはその後に続けます。
読みやすさと簡潔さは別物であり、読みやすさのほうが重要です。

出力を短くする方法は、含める内容を取捨選択すること（読み手の次の行動を変えない詳細は落とす）であって、文章を断片・略語・「A → B → 失敗」のような矢印の連鎖・専門用語に圧縮することではありません。
```

同じ「短い指示で制御する」考え方は、いつ手を止めるかというチェックポイントの判断にも応用できます。

---

## 4. 強力な指示追従（一時停止の判断）

**解説（要点）：**

- 同じ手法が長時間ワークフローのチェックポイント挙動にも有効。
- すべてのケースを列挙せずとも、本当にユーザーを必要とする場面だけで停止させられる。

**日本語訳：**

```
ユーザーの判断を仰ぐのは、作業が本当にそれを必要とするときだけにしてください——破壊的または不可逆な操作、実質的なスコープの変更、あるいはユーザーにしか提供できない入力です。
これらに該当したら、質問してターンを終え、約束で締めくくらないでください。
```

ユーザーに報告・確認する場面が出てくると、今度はその報告内容が事実に基づくことが重要になります。

---

## 5. 長時間実行中の進捗報告を根拠づける

**解説（要点）：**

- 長時間の自律実行では、実際のツール結果と照合して進捗を監査させる。
- Anthropicのテストでは、捏造を誘発する設計のタスクでも捏造された進捗報告がほぼ完全に排除された。

**日本語訳：**

```
進捗を報告する前に、各主張をこのセッションのツール結果と照合して確認してください。
証拠を示せる作業だけを報告し、まだ検証できていないものはその旨を明示してください。
結果は忠実に報告してください。
テストが失敗したならその出力とともにそう述べ、手順を飛ばしたならそう述べ、完了して検証済みなら言葉を濁さずはっきりとそう述べてください。
```

報告の正確さと並んで、勝手に動きすぎないこと——すなわち作業範囲の線引きも、長時間実行では課題になります。

---

## 6. 境界を明示する

**解説（要点）：**

- 要求外のアクション（依頼外のメール下書き、防御的なgitブランチのバックアップなど）を行うことがある。
- 行うべきこと・行うべきでないことを明示的に制約する。

**日本語訳：**

```
ユーザーが変更を依頼しているのではなく、問題を説明したり、質問したり、考えを口に出したりしている場合、成果物はあなたの評価です。
所見を報告して止まってください。
依頼されるまで修正を適用しないでください。
システムの状態を変えるコマンド（再起動、削除、設定変更）を実行する前に、その具体的な操作を証拠が実際に裏付けているか確認してください。
既知の障害にパターンとして一致するように見える兆候も、原因は別かもしれません。
```

ここまでは単一エージェントの振る舞いでしたが、Fable 5は複数のサブエージェントを並列に扱う場面でも能力が高まっています。

---

## 7. 並列サブエージェント

**解説（要点）：**

- 従来モデルより積極的に並列サブエージェントをディスパッチする。
- 頻繁に使い、委任の適切なタイミングを明示し、完了までブロックせず非同期通信を優先する。
- サブタスク間でコンテキストを保持する長寿命のサブエージェントは、キャッシュ読み取りで時間・コストを節約し、最も遅いサブエージェントがボトルネックになるのを避ける。

**日本語訳：**

```
独立したサブタスクはサブエージェントに委譲し、それらが実行されている間も作業を続けてください。
サブエージェントが脱線したり、関連する文脈を欠いていたりしたら介入してください。
```

複数セッション・複数エージェントの作業を積み重ねていくなら、そこで得た学びを残す仕組みが効いてきます。

---

## 8. メモリシステムを構築する（記録）

**解説（要点）：**

- 過去の実行から得た教訓を記録・参照できると特に高い性能を発揮する。
- Markdownファイルのような簡素なものでよいので、メモを書き込む場所を用意する。

**日本語訳：**

```
1つの教訓につき1ファイルで保存し、先頭に1行の要約を置いてください。
訂正も確認済みの方法も、なぜそれが重要だったかを含めて記録してください。
リポジトリやチャット履歴がすでに記録していることは保存しないでください。
重複を作るのではなく既存のメモを更新し、誤りと判明したメモは削除してください。
```

ゼロから始めるのではなく、既存の履歴からメモリを立ち上げることもできます。

---

## 9. メモリシステムを構築する（ブートストラップ）

**解説（要点）：**

- 既存の履歴からメモリシステムを立ち上げるには、過去のセッションをレビューさせる。

**日本語訳：**

```
これまで一緒に行ったセッションを振り返ってください。
サブエージェントを使って中心的なテーマと教訓を特定し、[X] に保存してください。
今後のために [X] を参照することを忘れないようにしてください。
```

長く自律的に走らせると、まれにではあるものの特有の挙動が現れることがあります。ここからはその対処です。

---

## 10. まれに発生する早期停止

**解説（要点）：**

- 長セッションの深い段階で、ツール呼び出しを発行せず意図表明のテキストだけでターンを終えたり、十分な情報があるのに許可待ちで停止したりすることがある。
- 「続けてください」「最後までやり切ってください」と伝えれば足りる。
- 一時停止の判断は、チェックポイント指示（本書4番）と組み合わせて定義する。
- 自律パイプラインでは、このプロンプトをシステムリマインダーとして追加する。

**日本語訳：**

```
あなたは自律的に動作しています。
ユーザーはリアルタイムで見ておらず、作業の途中で質問に答えることもできません。
そのため「〜しましょうか？」「〜してよいですか？」と尋ねると作業が止まってしまいます。
元の依頼から自然に導かれる可逆的な操作については、尋ねずに進めてください。
タスク完了後にフォローアップを提案するのは構いませんが、すでにユーザーと作業内容を話し合って合意したのに、着手前に改めて許可を求めるのはいけません。
ターンを終える前に、最後の段落を確認してください。
それが計画・分析・質問・次の手順のリスト、あるいはまだやっていない作業についての約束（「〜します」「〜したら教えてください」）であれば、今ツール呼び出しでそれを実行してください。
タスクが完了したとき、またはユーザーにしか提供できない入力で行き詰まったときにのみ、ターンを終えてください。
```

もう一つのまれな挙動が、残りコンテキスト量への過剰な反応です。

---

## 11. まれに発生するコンテキストバジェットへの懸念

**解説（要点）：**

- 非常に長いセッションで、新セッションの提案・要約による引き継ぎ・自身の作業削減をすることがある。
- ハーネスが残りトークンのカウントダウンを表示している場合に最も起きやすい。
- 可能なら明示的なバジェット表示を避け、表示が必要なら安心させる指示を添える。

**日本語訳：**

```
コンテキストはまだ十分に残っています。
コンテキストの制限を理由に、止まったり、要約したり、新しいセッションを提案したりしないでください。
作業を続けてください。
```

最後に、ユーザーとのやり取りそのものの質を高めるパターンです。まずは、依頼の背景を伝えることから。

---

## 12. リクエストだけでなく理由を伝える

**解説（要点）：**

- 意図を理解しているとより良い性能を発揮する。
- コンテキストがあると、自ら推測せずタスクを関連情報に結びつけられる。
- 特に複数ワークストリームを扱う長時間実行エージェントでは「なぜ依頼するか」を伝える。

**日本語訳：**

```
私は [対象者] のために [より大きなタスク] に取り組んでいます。
彼らは [出力によって可能になること] を必要としています。
それを踏まえて：[依頼内容]。
```

意図が伝わって出力の中身が良くなったら、その伝え方——読みやすさも整えます。

---

## 13. ユーザーとのコミュニケーションにおける読みやすさ

**解説（要点）：**

- 長時間・エージェント的な会話では読みにくいテキストを生成しがち（密な矢印省略記法、深い実装詳細、ユーザーが見ていない思考への言及、過度な専門用語）。
- コミュニケーションスタイルに関する補足指示で軽減できる。

**日本語訳：**

```
ツール呼び出しの合間の簡潔な略記は問題ありません（それはあなたが考えを巡らせている部分であり、そこでの簡潔さは良いことです）。
最終的な要約はそれとは異なります。
それは、その過程を一切見ていない読み手のためのものです。

ユーザーが見ていない間しばらく作業を続けていた場合（夜通し、何度ものツール呼び出しにわたって、あるいは最後に話してから）、あなたの最終メッセージは、その成果に対する彼らの最初の一瞥になります。
それは作業の流れの続きではなく、再接地（re-grounding）として書いてください。
まず結果、それから彼らに必要なこと1つか2つを、それぞれ初出であるかのように説明してください。
作業中に積み上げた語彙はあなたのものであって彼らのものではありません。
改めて導入しない限り、置いていってください。

最後に要約を書くときは、作業中の略記を捨ててください。
完全な文で書いてください。
用語は略さず綴ってください。
矢印の連鎖、ハイフンで積み重ねた複合語、自分で作ったラベルは使わないでください。
ファイル・コミット・フラグなどの識別子に言及するときは、それぞれにプレーンな言葉で独立した節を与えてください。
結果から始めてください。
何が起きたか、何が分かったかを一文で。
それから補足の詳細を。
短さと明確さのどちらかを選ばなければならないなら、明確さを選んでください。
```

読みやすい最終報告に加えて、作業の途中でも正確にメッセージを届けたい場合は、専用のツールを用意します。

---

## 14. ユーザー送信ツールを作成する

**解説（要点）：**

- 非同期エージェントで、ターンを終えずにユーザーが記載どおり正確に見る必要のあるメッセージを表示する手段。
- 対象：成果物（コードスニペット・下書き）、具体的な数値を含む進捗更新、ループ途中の質問への直接の返答。
- 呼び出されたら入力をそのままUIに描画し、ツール結果には簡単な確認応答を返す。
- ツール入力は要約されないため、内容がそのまま届く。
- UXが途中のコンテンツ配信や直接のやり取りに依存する場合に追加。日常的な進捗説明だけならモデル自身の要約で十分。

**日本語訳（説明文のみ翻訳・構造は維持）：**

```json
{
  "name": "send_to_user",
  "description": "メッセージをユーザーに直接表示します。進捗の更新、途中結果、またはタスク完了前にユーザーが記載どおり正確に確認する必要があるコンテンツに使用してください。",
  "input_schema": {
    "type": "object",
    "properties": {
      "message": {
        "type": "string",
        "description": "ユーザーに表示するコンテンツ。"
      }
    },
    "required": ["message"]
  }
}
```

## 15. 推奨されるスキャフォールディングの変更

**解説（要点）：**

原典の最終セクションは、個別のプロンプトではなく、移行時にハーネスやスキル側で行うべき変更をまとめています。

- **難易度範囲の最上位から始める。** 従来モデルに割り当てるより難しいタスクを選び、スコープ定義・明確化の質問・実行までを任せる。
- **長時間実行のプロンプトで自己検証を明示する。** 新しいコンテキストを持つ独立した検証サブエージェントは、自己批評よりも優れた結果を出す傾向がある（下記プロンプト）。
- **既存のプロンプトとスキルをリファクタリングする。** 従来モデル向けに開発されたスキルは Claude Fable 5 には指示が細かすぎることが多く、出力品質をかえって低下させる可能性がある。デフォルトの性能の方が優れている場合は、古い指示の削除を検討する。
- **Claude に推論を応答内で再現するよう指示しない。** 内部推論をエコー・書き起こし・説明させるプロンプトやスキルは `reasoning_extraction` 拒否カテゴリをトリガーし、Claude Opus 4.8 へのフォールバックが増加する可能性がある。移行時には、既存のスキルやシステムプロンプトに内省や思考過程の開示を求める指示がないか監査する。推論の可視性が必要な場合は、適応的思考の構造化された `thinking` ブロックを読み取り、長時間実行中の進捗表示には14番のユーザー送信ツールを使う。
- **ユーザー送信ツールを作成する。** 14番を参照。

**日本語訳（自己検証の指示）：**

```
作業を進めながら、[X] の間隔で自分の作業をチェックする方法を確立してください。
これを [X] の間隔ごとに実行し、サブエージェントを使って仕様に照らして作業を検証してください。
```

## 付録A: 移行チェックリスト

原典の各パターンは並列に列挙されていますが、導入の影響度と放置したときの実害には差があります。
以下は、何から手を付けるべきかを本ガイドが独自に整理した推奨順序です（原典に対応する記述はない、本ガイド独自の編集上の提案です）。

1. **ハーネスとタイムアウトの調整（パターン1）** — クライアントのタイムアウト・ストリーミング・進捗表示・非同期の実行確認を先に整える。全リクエストに影響し、怠ると正常に完了するはずだったターンがタイムアウトで失敗扱いになるため、他のすべてに先行する。
2. **既存プロンプト・スキルの `reasoning_extraction` 監査（パターン15）** — 思考過程の開示・内省を求める既存の指示を洗い出して除去または置換する。放置すると拒否とフォールバックが増えるという実害が出る数少ない項目のため、チューニング系より先に行う。
3. **エフォート方針の決定（パターン2）** — 既定の `high` を起点に、日常作業を `medium`／`low` へ下げる基準と、最重要タスクで `xhigh` へ上げる基準をチームで決める。コストとレイテンシの大半はここで決まる。
4. **抑制系プロンプトの導入（パターン1・2・3・4・6）** — 過剰な計画立て・要求外のリファクタ・冗長な報告・不要な停止を、本ガイドの短い指示でシステム層から抑える。1〜3で土台を整えたあとの挙動チューニングとして入れると、効果の有無を切り分けやすい。
5. **長時間自律実行の整備（パターン5・10・11）** — 進捗報告の根拠づけ・自律実行リマインダー・コンテキストバジェット表示の回避。自律パイプラインを運用する場合にのみ必要で、対話的な利用だけなら省略できる。
6. **継続的な投資（パターン8・9・14・15）** — メモリシステム、ユーザー送信ツール、独立した検証サブエージェント。導入即効性よりも、運用を重ねるほど効いてくる項目として最後に置く。

## 付録B: Claude Code への適用レシピ

「このガイドの使い方」で示した適用先を、Claude Code の具体的な機能に落とし込みます。
本付録の出典は Anthropic 公式の Claude Code ドキュメント（`code.claude.com/docs`）で、照合日は2026年6月11日です。

### 常時効かせる指示は CLAUDE.md 階層へ（パターン1〜6の置き場所）

- 配置場所は4スコープあり、組織全体（managed policy）→ ユーザー（`~/.claude/CLAUDE.md`）→ プロジェクト（`./CLAUDE.md` または `./.claude/CLAUDE.md`）→ 個人ローカル（`CLAUDE.local.md`、gitignore 推奨）の順に読み込まれます。
- 公式の目安は1ファイル200行以下で、長くなるほど遵守率が下がります。本ガイドの抑制系プロンプトを全部入りで貼るのではなく、効果を見ながら必要なものだけ選ぶことを推奨します（パターン15の「細かすぎる指示の削除」と同じ方向です）。
- 特定のファイル群にだけ効かせたい指示は、`.claude/rules/` 配下のルールファイルに `paths` frontmatter を付けてスコープできます。
- 出典: [How Claude remembers your project](https://code.claude.com/docs/en/memory)（照合日 2026-06-11）

### 繰り返しの注入は UserPromptSubmit hook（パターン10）

- 10番の自律実行リマインダーのような繰り返し注入する指示は、`UserPromptSubmit` hook の JSON 出力 `hookSpecificOutput.additionalContext` で実現できます。注入した内容は送信されたプロンプトと並んでコンテキストに追加されます。
- 発火するのはユーザーがプロンプトを送信したときで、モデルがツール呼び出しを続けている間は発火しません。原典が自作ハーネスに想定する「各アシスタントターンへの注入」より粒度は粗い点に注意してください。
- セッション冒頭に1回入れれば足りる文脈は、`SessionStart` hook（会話の先頭、最初のプロンプトの前に追加）を使います。
- hook スクリプトは `~/.claude/settings.json` または `.claude/settings.json` に登録し、スクリプトの標準出力で `additionalContext` を返します。

settings.json への登録：

```json
{
  "hooks": {
    "UserPromptSubmit": [
      {
        "matcher": "",
        "hooks": [
          { "type": "command", "command": "/path/to/inject-reminder.sh" }
        ]
      }
    ]
  }
}
```

スクリプト（上記の例では `inject-reminder.sh`）が標準出力へ返す JSON：

```json
{
  "hookSpecificOutput": {
    "hookEventName": "UserPromptSubmit",
    "additionalContext": "（ここに10番の自律実行リマインダーの本文を入れる）"
  }
}
```

- 出典: [Hooks reference](https://code.claude.com/docs/en/hooks)（照合日 2026-06-11）

### エフォートは `/effort` とスキル frontmatter で制御（パターン2）

- Claude Fable 5 の対応エフォートは `low`／`medium`／`high`／`xhigh`／`max` で、既定は `high` です（`max` はセッション限定）。
- セッション中は `/effort <レベル>`（引数なしでスライダー、`auto` でモデル既定にリセット）、起動時は `--effort` フラグ、恒常設定は settings の `effortLevel` で変更できます。
- スキル・サブエージェント定義の frontmatter `effort` で、そのスキル実行中だけレベルを上書きできます。「日常は `medium`、重い設計スキルだけ `xhigh`」のような使い分けを、定義側に固定できるのがプロンプトにない利点です。
- 出典: [Model configuration — Adjust effort level](https://code.claude.com/docs/en/model-config)（照合日 2026-06-11）

### メモリはまず組み込みの auto memory から（パターン8・9）

- Claude Code には auto memory が組み込まれており（v2.1.59 以降、既定で有効）、プロジェクトごとの `~/.claude/projects/<project>/memory/` に、索引 `MEMORY.md`（毎セッション先頭200行または25KBをロード）＋トピック別ファイルという構造で Claude 自身がメモを蓄積します。
- これはパターン8のプロンプトが指示する「1教訓1ファイル＋索引」とほぼ同型の構造が既に実装されている状態です。ゼロから Markdown メモリを設計する前に、`/memory` で組み込みの記録を確認・編集するところから始めることを推奨します。
- 出典: [How Claude remembers your project — Auto memory](https://code.claude.com/docs/en/memory)（照合日 2026-06-11）

### 安全性分類器のフォールバックは組み込み（「このガイドの使い方」の補足）

- API では自前のフォールバック実装が公式推奨ですが、Claude Code では分類器がフラグしたリクエストを既定の Opus モデルで自動的に再実行し、トランスクリプトに通知が表示されます（自動切替をやめて毎回確認したい場合は `/config` で変更可能）。
- リポジトリの CLAUDE.md やディレクトリ内容だけで初回リクエストがフラグされることがあり、原因の切り分けには `claude --safe-mode`（CLAUDE.md・スキル・MCP・hooks を無効化して起動）が使えます。
- 出典: [Model configuration — Automatic model fallback](https://code.claude.com/docs/en/model-config)（照合日 2026-06-11）

### 過剰な指示の削減は Claude Code でも公式推奨（パターン15）

- Claude Code の公式ドキュメント自身も Fable 5 の使い方として「手順ではなく結果を記述する」「検証のリマインダーは通常不要（自分で検証する頻度が高い）」と案内しており、パターン15の「従来モデル向けの細かすぎる指示は削除を検討」と同じ方向です。既存の CLAUDE.md・スキルの棚卸しは、付録Aのステップ2とあわせて行うと一度で済みます。
- 出典: [Model configuration — Work with Fable 5](https://code.claude.com/docs/en/model-config)（照合日 2026-06-11）

## 付録C: 既存スキルを棚卸しする同梱スキル `/fable5-tune`

付録A・Bが「何を・どの順で」整えるかの地図だとすれば、本付録はそのうち最も手作業が重いステップ——既存スキルの棚卸し（パターン15、付録Aのステップ2）——を Claude Code 自身に実行させるためのものです。本リポジトリには、既存スキルの SKILL.md を Claude Fable 5 向けに診断・リファクタする **`/fable5-tune` スラッシュコマンド**（`.claude/skills/fable5-tune/SKILL.md`）を同梱しています。いわば、本ガイドの「実行可能な付録」です。

このスキルは「能力の肩代わりは削り、本物の仕様だけ残す」を原則に、対象スキルの SKILL.md を1行（または1ブロック）単位で次の7分類にあて、「現状 → 案 ＋ 分類 ＋ 理由」の形式で書き換え案を提示し、承認を得てから適用します。

1. **推論出力の指示** — `reasoning_extraction` 拒否を誘発するため除去・置換（パターン15が求める監査に対応）
2. **能力の肩代わり** — 「段階的に考えて」のような、現行モデルが素で行う挙動の注意書きは削除
3. **挙動の列挙** — 同じ意図の指示の羅列は、短い原則1〜2文に圧縮（パターン3・4の応用）
4. **手順の固定** — ゴールと完了条件の記述に置換（順序自体に価値がある手順は残す）
5. **未要求の整理・リファクタ抑制** — 冗長な抑制ブロックは、パターン2の指示程度の短文に縮約
6. **重複** — 言い換えによる分散再掲も含めて、正となる1箇所に集約
7. **本物の仕様** — 出力フォーマット・ガードレール・承認ゲートなど、モデル能力と無関係な要件は保持

文面だけでは削除の可否が決まらない指示は、消さずに「要A/B」と分類してスキルあり／なしの比較検証を促します。「不要になった指示」と「テストが出番を作れていないだけの指示」を区別できる客観的な物差しは A/B 比較だけだ、という立場です。

付録A・Bと同じく原典に対応する見出しを持たない本リポジトリ独自の追加ですが、判断基準は原典のスキャフォールディング変更（パターン15）に基づいています。
