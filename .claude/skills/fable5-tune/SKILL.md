# fable5-tune / Fable 5 最適化

対象スキル（SKILL.md）を、Fable 5 の素の追従性能を活かす形に作り替える。原則は一つ：**能力の肩代わりは削り、本物の仕様だけ残す**。知見の多くは Fable 固有ではなく現行モデル全般に適用できる。

公式根拠: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5

## 進め方
1. 対象スキルの SKILL.md を 1 行（または 1 ブロック）単位で下の分類にあてる。
2. 分類に応じて書き換え案を作る。文面だけでは可否が決まらないものは「要A/B」に回す。
3. 変更案を「現状 → 案 ＋ 分類 ＋ 理由」で提示し、承認を待ってから適用する。

- **実務上の優先度**：実際に多いのは⑥（重複）と③④（手順・ゲートの反復）。①は必ず確認するが発火は稀。①を主役に据えて探し回らない。
- **コンテンツファイルは対象外**：対象が純粋な判定基準・テンプレ・データ等（モデルへの行動指示ではないもの）なら本分類はほぼ当たらない。過剰診断せず「内容ファイル＝対象外」と宣言する。
- **本スキル自体への自戒**：分類に but を継ぎ足さない。次に例外が必要になったら、但し書きを足すのではなくカテゴリの定義自体を書き直す。

## 分類と処理

### 1. 推論出力の指示 → 優先して探し、あれば除去・書き換え
「思考を明示せよ」「判断理由をすべて書け」「内部推論を本文に出力」など。
→ Fable では `reasoning_extraction` 拒否を誘発し、Opus へのフォールバックが増える。本文に書かせる指示を削る。可視化が要るなら、本文出力ではなく thinking ブロックを読む方式 / send-to-user ツール方式に置換する。
→ **最優先で探すが、よく作られたスキルには存在しないことも多い。無ければ「無し」と報告し、こじつけない。**
→ **境界**：「対象文書の §番号・引用を根拠に書け」のような、外部成果物の引用要求はこのカテゴリではない（内部推論の本文化ではないため）。これは要件として残す。

### 2. 能力の肩代わり → 削除（ただし現実性ガードは要A/B）
「段階的に考えて」「焦るな」「勝手に省略するな」「最後まで出し切れ」など、モデルの弱点を補うための注意書き。「読むのに Read、書くのに Write を使え」のような環境上自明なツール指定も含む。
→ 現行モデルは素でやる。ノイズになるので消す。
→ **注意**：「SF的シナリオを出すな」「非現実な例を避けよ」のような*現実性・品質を矯正するガード*は、旧モデル固有とは限らず**現行モデル全般で不活性**なことが多い（Fable も Opus も同様に振れない、という実測例がある）。ただし「不要」なのか「テストが出番を作れていない」のかは紛らわしい。即削除せず、**失敗モードを誘う入力で A/B 確認してから**判断する。

### 3. 挙動の列挙 → 一行に束ねる
同じ意図の指示を項目ごとに並べている箇所。
→ 指示追従が強いので短い原則一本で steer できる。列挙を 1〜2 文の原則に圧縮する。

### 4. 手順の固定（how の命令）→ 成果と完了条件に置換
「必ず A→B→C の順で」のような手続きの固定。
→ ゴールと成功基準を述べ、進め方は委ねる。Fable はタスクの中でスキルを自己更新するため、固い手順はむしろ逆効果になりやすい。
→ **見極め**：手順が*手法の本質*（順序自体が価値。例：要件懐疑→削除→最適化）なら残す。モデルが放っておいてもやる*認知の実況*（意味把握→話者把握→感情把握…のような内部手順の明文化）なら削る。
→ 「候補を2倍出してから絞れ」「最低3案出せ」のような、品質を出すための*手段の固定*も削る。Fable は直接良い出力を出せる。

### 5. 未要求の整理・リファクタ抑制 → 短い形に
冗長な YAGNI / 抑制ブロック。
→ 必要なら「タスクに必要な以上の機能追加・リファクタ・抽象化をするな。起こり得ないケースの防御を足すな。検証は境界（ユーザー入力・外部 API）だけ」程度の短文で足りる。既存の YAGNI 系スキルがあれば統合を提案する。

### 6. 重複 → 統合
同一の指示が複数箇所に書かれている。**逐語複製だけでなく、同じ制約が別の言葉で複数セクションに分散再掲されているケース**（例：方針・原則・チェックリストの別々のセクションに同じ趣旨が散る）も含む。同一ファイル内・SKILL.md と references 間の両方が対象。
→ 正となる1箇所に集約し、他は削除またはそこへの参照に置換する。トークンと保守コストを下げる。ただし、各 reference を単独で使う設計なら自己完結のための再掲は許容 → 迷えば要A/B。

### 7. 本物の仕様 → 残す（削らない）
出力フォーマット、文字数・言語・ペルソナ・ブランド、ガードレール、承認ゲート、ツール定義。
→ モデル能力と無関係な要件。能力が上がっても勝手には満たされない。診断はするが原則は保持する。

## 判断の指針
- 毎回「この行は能力の肩代わりか、それとも要件か」を問う。前者は削る、後者は残す。
- 文面だけで決まらない（デフォルトの方が良いか不明な）ものは消さず「要A/B」に分類し、スキルあり / なしの比較を促す。これが唯一の客観的な物差し。A/B 時は grader の健全性確認（canary：意図的な不良サンプルを検出できるか）と、失敗モードを誘う入力を含めること。これが無いと「不要」と「出番なし」を区別できず、一様な好スコアを誤読する。
- 忖度はしないが、安全・ガードレール・承認ゲートは保守的に扱う。迷ったら残して理由を添える。
- 自己検証チェックリストは一律に削らない。主観的な成果物に*具体的な判定基準*を与えているなら残す（公式も「検証できる具体物があると自己検証が効く」とする）。自明な挙動の再掲なら削る。
- 最小化は要件の取りこぼしを正当化しない。完了条件を満たさない削りはしない。

## 出力
変更ごとに：対象箇所 / 現状 / 案 / 分類番号 / 理由。末尾に「要A/B」項目の一覧と、削減した行数・文字数を 1 行で添える。承認後に対象ファイルを書き換える。
該当ゼロなら「変更不要」と一言で報告して終了する。変更を捻出しない。
